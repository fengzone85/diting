# Agent 自动更新方案

> 最后更新：2026-07-28
> 状态：设计阶段
> 默认：**关闭**

---

## 〇、你应该开启自动更新吗？

### 默认不需要

| 你的规模 | 推荐 | 理由 |
|---------|------|------|
| **1-20 台 VPS** | ❌ **不开启** | 手动更新足够，Agent 更新频率低（季度/半年一次） |
| **20-100 台 VPS** | 🤔 **看情况** | 手动批量部署可行，自动更新可选 |
| **100+ 台 VPS** | ✅ **建议开启** | 手动维护成本过高，自动更新收益大于风险 |

### 不需要开启的理由

1. **Agent 更新频率低**：Agent 功能稳定，通常季度甚至半年才更新一次
2. **手动更新足够**：`diting.sh --update-agent` 或 pssh 一条命令搞定
3. **风险收益比**：自动更新引入新的信任边界（CI/密钥管理），小规模部署不值得

### 开启前请确认

如果你决定开启自动更新，请确认你理解并接受以下风险：

| 风险 | 后果 |
|------|------|
| 签名私钥泄露 | 所有 Agent 可在 1 小时内被投毒 |
| GitHub 账号被盗 | 攻击者能发布恶意版本给你所有 Agent |
| 本地构建机被控 | 同上 |
| CI 供应链投毒 | 同上 |

**默认关闭 = 零额外风险。开启 = 你需要自己承担上述风险。**

## 一、核心理念（如果你决定开启）

**"Fork 即订阅，本地签名发布，签名即信任"**

| 原则 | 说明 |
|------|------|
| 不信任服务端 | Diting 服务端不发送任何指令 |
| 不信任 Diting 官方 | 代码开源但用户自行审核 |
| **只信任自己** | 用户 fork 仓库，本地签名发布 |

**信任边界**：收敛到用户自身的密钥管理和账号安全。

## 二、与项目安全哲学的关系

### 本项目原有底线

`README_EN.md` 第 237-247 行：

> "agents self-update by fetching an install script from the server and running `bash -s install` as root ... Both are command channels"

**原底线**："Agent 不执行任何远程代码"

### 本方案对底线的重新界定

| 方案 | 底线 | 项目立场 |
|------|------|---------|
| 服务端推送更新 | 执行服务端下发的代码 | ❌ 拒绝 |
| Diting 官方推送 | 执行 Diting 官方代码 | ❌ 拒绝 |
| **用户 fork + 用户签名** | **只执行用户自己签名过的代码** | ✅ 允许（用户自行决定） |

**底线的重新界定**：
> 从"Agent 不执行任何远程代码"演进为"Agent 只执行用户自己审核并签名的远程代码"。

### 风险转移，不是消除

| 信任锚点 | 失陷后果 |
|---------|---------|
| 服务端被控 | 所有 Agent 被控 |
| **用户私钥 + 账号失陷** | **所有 Agent 被控**（同量级） |

**本方案把风险从"服务端安全"转移到"用户自身的安全卫生"（密钥管理、账号安全），风险没有消失，只是锚点变了。**

### 与指令型 Agent（如哪吒）对比

| 维度 | 哪吒（指令型） | Diting（签名型） |
|------|--------------|----------------|
| 服务端权限 | **能向 Agent 发指令** | 只能接收上报 |
| 服务端被控后果 | **攻击者完全控制所有 Agent** | 只能看到监控数据 |
| 更新通道 | 服务端推送（Agent 必须执行） | 用户本地签名（Agent 只验签） |
| Agent 自主权 | 无（服务端说啥就做啥） | 有（只执行签名过的代码） |

| 攻击场景 | 哪吒 | Diting |
|---------|------|--------|
| 服务端被入侵 | ❌ **全网 Agent 被控** | ✅ 只泄露监控数据 |
| 管理员作恶 | ❌ **可推送恶意指令** | ✅ 无法影响 Agent |
| 账号/私钥泄露 | N/A | ⚠️ 可推送恶意版本（用户自己会发现） |

**关键区别**：
- 哪吒：服务端是"上帝"，Agent 没有拒绝能力
- Diting：即使服务端被完全控制，攻击者也无法向 Agent 推送任何代码

**结论**：Diting 自动更新的风险是"用户自身账户安全"，指令型 Agent 的风险是"服务端全权控制"。前者由用户自主管理，后者完全依赖服务端可信。

## 三、真实攻击面（如果你决定开启）

### 真正的威胁（按可能性排序）

| 威胁 | 现实可能性 |
|------|-----------|
| CI 供应链投毒（恶意 action、依赖混淆） | **高** |
| GitHub 账号被盗（无 2FA、钓鱼） | **高** |
| 本地构建机被控（恶意软件） | **中高** |
| 外人改你私有仓库 | 极小 |

### Agent 被控泄露面

| 凭证 | 泄露后果 | 风险 |
|------|---------|------|
| `SIGN_PUBKEY` | 公钥本就可公开 | ✅ 无风险 |
| `UPDATE_REPO` | 仓库 URL 是公开信息 | ✅ 无风险 |
| `AGENT_TOKEN` | 只能伪造本机数据 | ✅ 项目已承认 |

### 零入站保证

本方案**不新增任何入站端口**，保持 Agent 纯单向上报模型。

## 四、架构概览

```
用户（本地签名）
    │
    ├─ fork diting-agent 仓库
    ├─ 审核上游更新代码
    ├─ push tag → GitHub Actions 编译（CI 不持私钥）
    ├─ 下载构建产物
    ├─ 本地签名（私钥永不离开本机）
    └─ 上传 .sig 到 Release
                                    │
                                    ▼
                            GitHub Release
                                    │
                                    │ Agent 每小时检查（只读）
                                    ▼
                            Agent 下载 + 验证签名
                                    │
                                    ▼
                            通过 → 原子替换 + 重启
```

## 五、用户操作流程（如果你决定开启）

### 5.1 首次配置

```bash
# 1. Fork diting-agent 到个人仓库
# 2. 生成签名密钥（本地执行）
openssl genpkey -algorithm Ed25519 -out update-private.pem
openssl pkey -in update-private.pem -pubout -out update-public.pem

# 3. 在 Agent 上启用（通过环境变量）
export AUTO_UPDATE=1
export UPDATE_REPO=https://github.com/你的/diting-agent
export SIGN_PUBKEY="$(cat update-public.pem)"
```

### 5.2 发布新版本

```bash
cd ~/projects/diting-agent-fork

# 合并上游更新
git pull upstream main
git diff HEAD~1  # 审核代码

# 发布
git tag v1.1.0
git push origin v1.1.0

# 等待 CI 构建完成，然后本地签名
make sign  # 私钥本地执行

# 上传签名
gh release upload v1.1.0 dist/*.sig
```

### 5.3 回滚

```bash
git push origin --delete v1.1.0
gh release delete v1.1.0
# Agent 自动回滚到上一版本
```

## 六、签名验证

### 签名算法：Ed25519

```go
// Agent 端验证（传原文，不预哈希）
ed25519.Verify(publicKey, binaryBytes, signature)
```

### 本地签名（私钥不进 CI）

```bash
for binary in dist/*; do
  openssl dgst -sha256 -sign update-private.pem \
    -out "${binary}.sig" "${binary}"
done
```

**关键约束**：
- 私钥只在本地存在
- CI 只负责编译，不负责签名
- 签名由用户在本地执行后上传到 Release

## 七、安全约束

| 约束 | 说明 |
|------|------|
| **默认关闭** | `AUTO_UPDATE=0` |
| **私钥本地保管** | 永不上传 CI/GitHub/任何远程 |
| **CI 只编译不签名** | 签名由用户在本地执行 |
| **Agent 禁止写凭证** | 严禁 `GITHUB_TOKEN`/`PAT` |
| 签名强制 | Ed25519，失败不更新 |
| 用户仓库 | 只监听用户指定的仓库 |
| 原子更新 | 失败自动回滚 |
| Token 不进命令行 | 环境变量传入 |
| 服务端代理 | 限速问题由服务端解决 |

## 八、常见问题

### Q：我需要开启自动更新吗？

**大多数用户不需要。** 如果你有 10-20 台 VPS，Agent 更新频率低（季度/半年），手动更新 `diting.sh --update-agent` 或 pssh 一条命令搞定。

### Q：自动更新有什么风险？

**签名私钥或 GitHub 账号失陷 = 所有 Agent 可在 1 小时内被投毒。** 这是与服务端被控同量级的风险。

### Q：为什么私钥不进 CI？

CI 持有私钥 = 信任 GitHub + CI + 所有第三方 action。一次供应链投毒 = 私钥泄露。本地签名才能让"信任自己"真正成立。

### Q：100+ 台 VPS 怎么办？

可以考虑开启，但需要：
- 妥善保管私钥（推荐 YubiKey 或离线存储）
- GitHub 账号启用 2FA
- 服务端代理解决 GitHub API 限速
