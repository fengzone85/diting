# 安全设计

DiTing 的安全模型建立在三个支柱之上。

## 三大支柱

### 1. 无指令通道

受控端（Agent）**不监听任何端口**，仅向服务端发起出站 HTTPS 请求。
服务端没有任何 API 可以向 Agent 下发指令。

**这意味着**：即使服务端被完全攻破，攻击者也无法通过 Agent 执行任何操作。

### 2. Agent 零耦合

Agent 之间互不通信，互不知道彼此存在。
一个 Agent 被攻破不会影响其他 Agent。

### 3. 数据最小化

采集仅限系统状态指标（CPU/内存/磁盘/流量/温度等），**不包含**：
- 进程列表
- 系统配置
- 网络连接
- 用户信息
- 密钥/凭据
- 内核版本 / CPU 型号 / GPU 型号（可匹配漏洞的指纹）

采集数据对攻击者无可利用价值。

#### 指纹的风险有两个维度：定位，与聚类

常见直觉是：「Agent 零入站、不采公网IP、不接受指令，采什么都连不上，所以指纹无害。」这只看了一半。

| 维度 | 攻击者要解决的问题 | 靠什么防 |
| --- | --- | --- |
| **定位** | 这台机器在哪？怎么连上？ | 不采公网IP + 零入站 |
| **聚类** | 已落地一台，**哪些机器能用同一套 exploit 再打一遍？** | 不采可匹配漏洞的指纹 |

**聚类不需要定位能力。** 攻击者若已通过无关入口拿到一台机器的 shell，DB 里任何能分组的字段都会降低他的二次扩散成本：内核版本直接匹配 CVE；CPU 型号识别微架构（同型号机器漏洞面相同，攻陷一台即拿到该型号全部机器的攻击配方）；端口/进程清单本身就是一份待办清单。

因此「无公网IP」防的是「找不到你」，「不采内核/CPU型号」防的是「找到后知道打哪里」——两条独立防线，前者不能替代后者。

## 安全措施清单

### 鉴权与会话

| 措施 | 说明 |
|---|---|
| TOTP 2FA (RFC 6238) | 管理员登录需动态验证码（可选启用，非强制） |
| 恒定时间比较 | Token 比较 `SHA-256 + timingSafeEqual`，消除长度侧信道 |
| HttpOnly Cookie | Session Cookie 不可被 JS 读取 |
| 登录限速 | 防暴力破解 |

> 目前**没有** 2FA 一键重置 / 恢复令牌，丢失设备需改库处理，见文末「TOTP 2FA → 2FA 重置」。

### 受控端加固

| 措施 | 说明 |
|---|---|
| HTTPS 强制 | 非 localhost 请求 `exit(1)` |
| 401/403 长退避 | 认证失败退避 600 秒，防爆破 |
| 非 root 运行 | Docker 内 uid 1000（用户 `diting`）+ 只读挂载 `/:/host:ro` |
| systemd 加固 | `NoNewPrivileges`、`ProtectSystem=strict`、`ProtectHome`、`ReadWritePaths=/var/lib/diting`、`PrivateTmp`（共 5 项，见《受控端部署》） |
| 无 shell 调用 | `probe_one()` 使用 list 形式命令，不经过 shell |
| 本地固定探测目标 | 探测目标写在 agent 本地环境变量；**运行期**服务端无任何下发通道（安装期由一键命令注入一次） |

### 传输安全

| 措施 | 说明 |
|---|---|
| HTTPS 白名单 | 受控端仅信任配置的 Server URL |
| CSP 头 | 服务端设置 Content-Security-Policy |
| Token 哈希存储 | 数据库存储 SHA-256 哈希，非明文 |

### 前端安全

| 措施 | 说明 |
|---|---|
| XSS 防护 | 所有用户输入经转义 |
| CSRF 防护 | Cookie + SameSite |
| 输入校验 | `validate.js` 统一校验 |

## 数据保留

服务端每小时自动清理过期指标，防止数据库无限膨胀。保留天数可在「设置 → 站点与界面」配置（7-3650 天），也可通过环境变量 `RETENTION_DAYS` 设置（默认 30 天）。后台设置优先级高于环境变量，保存后 1 小时内自动生效，无需重启。

## 数据备份

数据库是监控系统的核心资产（含全部 Agent 记录、历史指标、设置），建议定期备份：

```bash
# 一键备份（热备份，不中断服务）
sudo bash diting.sh --backup

# 安装每日自动备份（写入 cron，含恢复请求处理行；幂等）
sudo bash diting.sh --backup-schedule install
```

备份文件默认存到 `/var/backups/diting/`（压缩优先 `pigz`，无则回退 `gzip`，体积约为库的 20%），包含完整
数据库快照。恢复前会自动备份当前状态，确保可回滚。新增的备份状态与操作都会
写入 audit_logs（下载 / 删除 / 请求恢复均可审计）。

## TOTP 2FA

DiTing 支持 TOTP（基于时间的一次性密码），兼容 Google Authenticator、1Password 等。

### 启用流程

1. 登录管理面板
2. 进入设置 → 安全
3. 手动输入密钥到 TOTP 应用（Google Authenticator / 1Password 等；本项目不调用外部二维码服务，符合 CSP）
4. 输入 6 位验证码确认

### 2FA 重置

目前**没有**一键重置 2FA 的开关，也没有「启用时生成的一次性重置 Token」——`diting.sh --reset-admin-token`
只重置 `ADMIN_TOKEN`，**不影响** 2FA 状态。丢失设备时需 SSH 登录服务器改库关闭：

```sql
-- 库位置：Docker 部署为 diting-server 容器内 /data/monitor.db（DB_PATH 可改）；
-- 原生部署为 server/ 实际使用的库。可用 sqlite3 <库文件> 执行：
DELETE FROM admin_config WHERE key IN ('admin_2fa_secret', 'admin_2fa_enabled');
```

执行后重启服务（容器重建 / `systemctl restart`），即可用管理员 Token 登录，并在「设置 → 安全」重新绑定 2FA。

## 信任边界

```
┌─────────────────────────────────────────┐
│  服务端 VPS                              │
│  ┌───────────┐    ┌──────────────────┐  │
│  │  Agent A  │───▶│                  │  │
│  └───────────┘    │   Server (Node)  │  │
│  ┌───────────┐    │   + SQLite       │  │
│  │  Agent B  │───▶│                  │  │
│  └───────────┘    └──────────────────┘  │
│  ┌───────────┐                          │
│  │  Agent C  │───▶ (只出站，不监听)      │
│  └───────────┘                          │
└─────────────────────────────────────────┘

信任边界：每个 Agent 独立，互不通信
攻击面：仅服务端 Web 端口
```
