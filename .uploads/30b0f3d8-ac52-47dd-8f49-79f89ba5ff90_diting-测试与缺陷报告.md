### BUG-1（P1）在线状态多源判定，同一节点同时在线又离线

**现象**：把「设置中心 → 离线阈值」改为 10s，agent 停止 20s 后，节点列表显示离线，但详情页/仪表盘/公开页显示在线。

**复现**（脚本 `repro/online-status.js`，可直接运行）：

```
UI offline_sec=10 / env OFFLINE_THRESHOLD_SEC=60 / last_seen=now-20s
  /api/agents              status=200 online=false
  /api/agents/:id          status=200 online=true
  /api/overview            status=200 online=1
  /api/v1/nodes            status=200 online=true
  /api/public/agents       status=200 online=true
```

**根因**：在线判定有两套实现。

- `GET /api/agents` 已经按「节点覆盖 > 分组覆盖 > 全局」解析阈值（`alerts.resolveAgentThresholds`），是正确实现；
- `GET /api/agents/:id`、`/overview`、`/public/overview`、`/public/agents` 仍直接读 `Number(process.env.OFFLINE_THRESHOLD_SEC || 60)`；
- `src/v1.js`、`src/compat.js` 又各自复制了一份环境变量实现，且比较符一个用 `<` 一个用 `<=`。

只要管理员在 UI 里改过阈值（UI 值优先于 env），或者给节点/分组配了覆盖值，这些接口就必然与告警、节点列表不一致。仪表盘的在线数、公开页状态、Komari 兼容层全部受影响。

**修复**：新增 `server/src/online.js` 作为唯一判定源，导出 `buildCtx()/isOnline()/onlineTtl()`，`api.js`、`v1.js`、`compat.js` 全部改为调用它；批量接口复用一次 `buildCtx()`，避免逐节点查覆盖表。

```js
function isOnline(a, now = Date.now(), ctx) {
  if (!a || !a.last_seen) return false;
  return now - a.last_seen < effectiveOfflineMs(a, ctx);
}
```

修复后同一脚本输出全部为 `false`，5 个入口一致。

### BUG-2（P1）新建节点立即收到「离线」告警

**现象**：后台创建一个节点，agent 还没安装，告警系统第一轮检查就发「[监控] xxx 离线」；等 agent 装好开始上报，又收到一条「已上线」。每个新节点必然产生一对噪音通知。

**复现**（`repro/never-reported-alert.js`）：

```
新建节点 last_seen = 0 （0 表示 agent 尚未安装/首次上报）
首次检查触发的通知: [{"event":"offline","subject":"[监控] brand-new-node 离线"}]
```

**根因**：`alerts.checkAgent` 里

```js
const online = a.last_seen && (now - a.last_seen) < c.offlineSec * 1000;
if (!online) { ...发离线告警... }
```

`last_seen = 0` 被当成「1970 年至今都没上报」，直接落入离线分支；同时写入内存态 `OFFLINE_SINCE`，导致首次心跳后还会补发「已上线」。而 `last_seen = 0` 的真实语义是「尚未上报」，不是「离线」。

**修复**：从未上报直接跳过判定，也不记录离线起点：

```js
if (!a.last_seen) return null;
const online = (now - a.last_seen) < c.offlineSec * 1000;
```

修复后脚本输出 `[]`。注意这里的语义是「首次心跳之前不产生任何告警」——如果产品希望「建节点后 N 分钟未安装也提醒」，应该用独立的 `install_timeout` 事件，而不是复用离线告警。

### BUG-3（P1）`PUT /api/settings` 局部提交清空全站设置

**现象**：只想改一个离线阈值，调用

```http
PUT /api/settings
{"ui":{"alert":{"offline_sec":60}}}
```

返回 `{"ok":true}`，但站点标题、描述、`agent_server_url`、公开开关、背景、公告等全部被重置。随后创建节点直接失败：

```
400 {"error":"server_url_not_configured"}
```

**根因**：`db.setUiSettings` 是整体覆盖写，而路由只对 `admin_dashboard_layout` 做了「未传则保留」的特判。任何只提交部分字段的调用方（脚本、第三方面板、前端漏字段、旧版本前端）都会把其余配置抹掉。`ui.alert` 还是浅合并，只传 `offline_sec` 会连 `cpu_pct/mem_pct` 一起丢。

**复现记录**（本地实例）：

```
before: Diting 监控  http://127.0.0.1:8081  {cpu_pct:90, mem_pct:90, disk_pct:90, temp_c:80, offline_sec:60}
PUT {"ui":{"alert":{"offline_sec":45}}}
after:  ""           ""                     {offline_sec:45}
```

**修复**：写入前与旧值做深合并（数组整体替换，普通对象递归合并），并移除只针对布局字段的特判：

```js
const isPlainObject = (v) => !!v && typeof v === 'object' && !Array.isArray(v);
function mergeUiSettings(base, patch) {
  const out = Object.assign({}, base);
  for (const [k, v] of Object.entries(patch)) {
    out[k] = isPlainObject(v) && isPlainObject(out[k]) ? mergeUiSettings(out[k], v) : v;
  }
  return out;
}
db.setUiSettings(mergeUiSettings(uiBefore, b.ui));
```

修复后同一请求：`site_title`、`agent_server_url` 保留，`alert` 变为 `{cpu_pct:90, mem_pct:90, disk_pct:90, temp_c:80, offline_sec:45}`。`notify` 配置本来就在 `db.setNotifyConfig` 内部做了合并，无需改动。

### BUG-4（P1）磁盘 IO 统计把分区与整盘重复累加

**现象**：agent 上报的磁盘读写速率约为真实值的 1.8 倍（写方向），导致磁盘 IO 图表、AI 日报、容量趋势全部偏高。

**证据**：本机 `/proc/diskstats` 同时存在 `vda`、`vda1`、`vda2`，`vda` 的扇区数约等于两个分区之和：

```
设备       读扇区     写扇区
vda        1,180,013  32,596,856
vda1           1,264           0
vda2       1,176,157  32,596,848
...
按 agent 现有口径合计：读 7,157,104  写 71,985,264
只算整盘：            读 5,979,359  写 39,388,416
写方向虚增 1.83 倍
```

**根因**：`agent-go/collector/diskio.go` 只过滤了 `ram/loop/zram/dm-/md`，随后对所有剩余设备累加 `fields[5]/fields[9]`。Linux 的 `/proc/diskstats` 中整盘和分区都会出现，分区数值是整盘的子集。

**修复**：用 sysfs 判断分区并跳过。不能用「名字以数字结尾」，因为 `nvme0n1` 这类整盘名也以数字结尾：

```go
if _, err := os.Stat("/sys/class/block/" + dev + "/partition"); err == nil {
    continue
}
```

新增回归用例 `agent-go/collector/diskio_test.go`：独立解析 `/proc/diskstats` 计算整盘合计，与 `diskIO()` 输出比对；没有分区的主机自动 skip。修复后输出：

```
分区 vda1 已跳过 ...
分区 vda2 已跳过 ...
整盘合计 r=3061638656 w=20560719872，与 diskIO 输出一致（分区已剔除）
```

### BUG-5（P2）磁盘计数器回退导致 uint64 下溢，出现 TB/s 尖刺

**现象**：虚拟机磁盘重建、热插拔、云盘重置后，下一次上报的 `disk_r_rate/disk_w_rate` 出现 `1e15` 量级（服务端上限）的尖刺，图表被压平，AI 分析会把它当成异常。

**根因**：`agent-go/collector/linux.go`

```go
diskRRate = float64(dr-c.prevDiskIO.read) / dt   // dr、prev 都是 uint64
```

网络分支有 `if rx > c.prevNet.rx` 保护，磁盘分支没有。计数器回退时无符号相减下溢：

```
0 - 1000 = 18446744073709550716
/ 10s     = 1.845e18 B/s ≈ 1,844,674 TB/s
```

服务端 `validate.js` 把 `disk_r_rate` 钳到 `1e15`，所以最终落库的是「1000 TB/s」，仍然是一个荒谬值。

**修复**：与网络分支保持一致，仅在单调递增时计算速率：

```go
if dr >= c.prevDiskIO.read { diskRRate = float64(dr-c.prevDiskIO.read) / dt }
if dw >= c.prevDiskIO.write { diskWRate = float64(dw-c.prevDiskIO.write) / dt }
```

代价是计数器重置的那一个采样点速率为 0，而不是伪造一个巨大值——这是监控系统应有的降级行为。

### BUG-6（P2）HTTP 部署下退出登录无效

**现象**：按 README 的本地调试方式设置 `ADMIN_ALLOW_HTTP=1`，通过 `http://<内网IP>:8081` 登录后台，点「退出登录」后刷新页面仍是登录态。

**证据**（同一台服务、同一会话）：

```
POST /api/login  → Set-Cookie: hm_session=...; HttpOnly; SameSite=Strict; Path=/; Max-Age=43200
POST /api/logout → Set-Cookie: hm_session=; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=0
```

登录 Cookie 不带 `Secure`（为了兼容 http），注销 Cookie 却固定带 `Secure`。浏览器会把「带 Secure 的删除指令」视为不同 Cookie 而拒绝覆盖，旧会话继续有效。`localhost` 下 Chrome 对 Secure Cookie 有豁免，所以本机测试很容易漏掉，一旦用内网 IP 访问就复现。

**修复**：登录/注销共用同一个属性构造函数：

```js
function sessionCookieAttrs(maxAgeSec) {
  const secure = process.env.ADMIN_ALLOW_HTTP === '1' ? '' : 'Secure; ';
  return `HttpOnly; ${secure}SameSite=Strict; Path=/; Max-Age=${maxAgeSec}`;
}
```

修复后注销响应为 `hm_session=; HttpOnly; SameSite=Strict; Path=/; Max-Age=0`，与会话 Cookie 属性一致。

### BUG-7（P2）告警轮询周期忽略节点/分组覆盖值

**根因**：`alerts.start()` 只用全局 `offline_sec` 推导轮询间隔：

```js
const interval = Math.max(10000, (offlineSec * 1000) / 2);
```

而 `checkAgent` 支持「节点 > 分组 > 全局」。若全局阈值 3600s、某节点覆盖 30s，检查每 30 分钟才跑一次，该节点的离线告警最多迟到 30 分钟，覆盖值等于失效；反过来，全局 10s、节点 3600s 时又会每 5 秒空转全表。

**修复**：取全局值与所有覆盖值的最小值：

```js
let minOverride = Infinity;
for (const r of db.listAlertOverrides()) if (r.offline_sec && r.offline_sec < minOverride) minOverride = r.offline_sec;
for (const r of db.listGroupAlertOverrides()) if (r.offline_sec && r.offline_sec < minOverride) minOverride = r.offline_sec;
const interval = Math.max(10000, (Math.min(offlineSec, minOverride) * 1000) / 2);
```

覆盖值在运行期修改后仍需重启才生效，这一点与修复前一致；若要热更新，应在覆盖写接口里重置定时器。

### BUG-8（P2）默认「慢档 60s + 离线阈值 60s」，零余量必然误报

**证据链**：

- `agent-go/config/config.go`：`Adaptive = true`（默认开），`SlowInterval` 默认 **60s**；
- 同文件注释与 README 第 411 行都写着「慢档 60s 需服务端 `OFFLINE_THRESHOLD_SEC ≥ 120`」；
- 但 `server/.env.example`、README 参数表、`db.getUiSettings()` 的默认值全是 **60**。

也就是说，按文档默认值部署，平稳期每 60s 上报一次，判定阈值也是 60s，任何一次 GC、网络抖动、磁盘慢 IO 都会让 `now - last_seen` 越过 60s，触发离线告警，随后下一次上报又触发「已上线」。`checkOfflineThresholdSanity()` 会在启动时打一条 warning，但它要求已有 agent 的观测间隔，等于「已经误报过才提醒」。

**建议方案**（二选一，未纳入补丁，因为会改变产品默认行为）：

1. 把 agent 默认 `SLOW_INTERVAL` 调成 30s（阈值 60s 的两倍关系成立，改动最小，代价是流量略增）；
2. 或把服务端三处默认值（`.env.example`、UI 默认、`resolveAlertThresholds` 兜底）统一改成 120s，并同步 README 参数表。

我更倾向方案 2：与现有文档描述一致，且不增加 agent 上报频率。注意 `test/security-fixes.test.js` 有一条断言硬编码「无 UI 无 env 时回退 60」，改默认值时要同步更新该断言。

### BUG-9（P2，环境相关）Docker 宿主机网卡聚合重复计算容器流量

`agent-go/collector/network.go` 累加 `/proc/net/dev` 中所有非 `lo` 接口。以 `--network host` 运行的 agent 在 Docker 宿主机上会同时看到 `eth0`、`docker0`、成对的 `vethXXX`：

- 容器发出一个包：`veth` 宿主端计一次，`docker0` 计一次，`eth0` 再计一次；
- 容器之间通信甚至完全不经过 `eth0`，也会被计入「公网流量」。

对本项目主打的「月流量配额/超量告警/计费」来说，这会直接放大 2–3 倍。当前沙箱没有 Docker（只有 `eth0`），因此未能实测复现，但代码路径是确定的。

**建议**：优先只统计默认路由所在接口（解析 `/proc/net/route` 的 `Destination=00000000`），取不到时退回「所有物理接口」，并跳过 `veth*/docker*/br-*/virbr*/tun*/tap*` 等虚拟前缀。若产品确实想统计「所有转发流量」，应在文档里写清楚口径，避免与云厂商计费口径对不上。

### BUG-11（P3）`public_enabled` 类型不安全，字符串 `"no"` 关不掉公开页

公开路由的门控是：

```js
if (ui.public_enabled === false) return publicDisabled(res);
```

只有严格的布尔 `false` 才会关闭。若配置来自 API、旧版本或导入文件，值是 `"no"`/`"0"`/`0`，公开页仍然对外开放（兼容层 `compat.js`/`v1.js` 用的是 `!== false`，同样如此）。我在测试中写入 `"no"` 后，`GET /api/public/agents` 依然返回 200 和节点数据。

**建议**：抽一个 `publicEnabled(ui)`，按 `false | 'false' | 'no' | '0' | 0` 归一化为关闭，并在 `PUT /settings` 落库前强制转布尔。正常 UI 复选框写的是布尔值，所以这个问题目前只影响 API/迁移场景，定为 P3。

### BUG-12（P3，待决策）计费按 UTC 日界、续期按本地日界

`billing.js` 明确按 UTC 整日差计算（并有测试 `UTC 口径：临界日期不受本地时区影响` 锁定），而 `renew.js` 明确按本地日历日计算，`util.daysUntil` 也是本地口径。结果在 UTC+8、到期日为 2026-10-23 时：

```
10-23 00:30 本地  computeBilling: active, remaining_days=1
10-23 09:00 本地  computeBilling: expired, remaining_days=0
10-23 23:30 本地  computeBilling: expired
```

同一个本地自然日内，08:00 前后状态翻转；同时仪表盘的「即将到期」用 `daysUntil` 显示 0 天，节点卡片却显示「剩余 1 天」。这不是数据错误，但会让运营以为「凌晨还有一天，早上就过期了」。

**建议**：统一成 `renew.js` 的本地日历日口径（`new Date(y,m,d)`），并明确「到期日当天是否可用」这一语义；若要保留 UTC 契约，则把 `daysUntil` 与告警的到期判断也改成 UTC，至少做到同一后台页面口径一致。改动会触碰现有测试断言，因此本轮未纳入补丁。

## 四、审计覆盖与未发现问题的区域

以下区域做了针对性验证，未发现可复现缺陷，供后续回归参考：

## 五、优先级建议

如果只修三个，建议按这个顺序：**BUG-1（状态自相矛盾，用户第一时间会报障）→ BUG-2（新节点告警噪音，直接影响告警可信度）→ BUG-3（一个局部设置请求能打瘫建节点功能）**。

BUG-4/5 属于数据正确性，修复成本很低，建议一并合入；BUG-8 是默认值问题，改动一行但要同步文档和测试断言，适合单独一个 PR；BUG-9 需要产品先确认流量口径，再动代码。

从工程角度看，这个项目的基础相当扎实：464 个服务端用例、鉴权矩阵、备份/SSRF 防护都做得比多数同类项目细。真正的问题集中在「同一份配置被多个入口各自解释」——在线阈值、日界口径、流量口径都是同一类病根。建议后续把「配置解析」也像 `online.js` 这样收敛成单一模块，并在 CI 里加一条「禁止路由直接读 `process.env.OFFLINE_THRESHOLD_SEC`」的 lint 规则，防止再次分裂。
